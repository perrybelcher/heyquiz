# Bounded manual journey cases — design only

12 October 2026. Read-only review of the current journey evaluator, fixtures, transfer, player field renderer and scoring. No application changes, tests, respondent sessions, network requests or provider calls were made in this pass. Installed Next client-boundary guidance and AGENTS.md were read.

## Recommendation

A safe bounded implementation is possible **without changing the form schema, published snapshots, actual routing/scoring, server storage or respondent APIs**. Add one optional **Add manual test case** action inside Journey testing. Let creators supply synthetic `number` and `short_answer` values alongside existing finite choices, evaluate exactly one current-draft path, review its observed expectations, then explicitly save a new case. Leave automatic representative/enumerated testing unchanged. A manual case never increases its exhaustive-path count.

This does require a small, versioned extension to the browser fixture/transfer codec. Merely accepting arbitrary strings or numbers in today's `answers` union would lose type provenance, blur option IDs with text and weaken existing privacy/validation boundaries. Do not implement that shortcut.

## Proposed exact input and fixture contract

1. Support the existing `singleTypes`, `multiTypes`, terms and checkbox controls, plus **only** exact question types `number` and `short_answer`. Allow an explicit unanswered choice. Display steps remain display-only. Do not add currency, ratings/sliders, paragraph, dates, hidden/prefill, calculations, matrices/ranking, contact fields, passwords, files, signatures or challenges in this increment. Required reached unsupported inputs prevent a save; optional unsupported inputs may remain omitted with a clear untested-input notice, matching existing simulation limits. A reached captcha still blocks evaluation. Never fabricate a hidden value or contact capture payload.
2. Choice payloads remain existing option IDs / unique option-ID arrays / actual booleans. Number payloads are strings, at most **64 characters**, with explicit decimal/scientific notation syntax and a finite `Number(value)`; reject hex, Infinity, NaN, object/array coercion and unfinished numeric input. Preserve accepted lexical text and let real `validationError` enforce bounds. Do not claim step validity. Blank is an omitted answer, never zero.
3. Short-answer payloads are strings at most **256 UTF-16 code units**, with no control characters, line breaks, bidi-format controls or unpaired surrogates. Preserve case, spaces and Unicode rather than silently normalizing/truncating. Whitespace-only input is treated as unanswered for the composer. These are storage/UI limits for synthetic fixtures, not new respondent rules. A rule/key beyond these bounds is out of this manual tool's scope, with Preview offered separately.
4. Keep legacy case objects untouched. Add a strict manual case variant using `inputVersion: 2` and `typedAnswers: Record<questionId, { type: "number" | "short_answer"; value: string }>`. Existing `answers` continues to hold finite choices only. Require disjoint question keys, at most **200 combined answers**, safe non-reserved IDs and no unknown nested fields. Require at least one typed entry for the new variant; a manually authored choice-only case can retain the legacy case shape. New cases always save the full existing expectation set.
5. Merge the two answer maps only in a pure adapter immediately before real evaluation. Verify every supplied ID exists and each typed entry still has its recorded exact question type. A deleted question/type change is a concrete failed check, never an automatic reinterpretation. Ignore no supplied unsupported payload silently, even if that question would be skipped. After resolving, prepare a baseline containing only answers on that path; keep any now-hidden editor inputs in volatile state so changing an earlier answer does not silently lose work. Show that omitted/hidden input values are not part of the proposed saved case.
6. Case IDs stay independent `case-${crypto.randomUUID()}` values. References stay question/option/category/section IDs, never array positions or labels. Changing text/style makes the fingerprint stale but does not by itself change the asserted behavior. No renumbering, guessed remapping or auto-upgrade on question replacement.

`Answers` is already `Record<string, unknown>`, so this adapter does not require a scoring model migration. The tighter stored fixture union is intentionally narrower than that runtime type.

## Explicit review, storage and portability

Suggested helpers in a new client-safe `lib/manual-journey.ts`: `validateManualJourneyInput`, `prepareManualJourneyCase` and `applyManualJourneyCase`. Prepare returns the immutable supplied-input baseline, current draft fingerprint, library baseline, resolved path, exact evaluated case and proposed expectations. Confirm revalidates and reevaluates against the same input and draft; it rejects stale/tampered results rather than trusting a caller-supplied `JourneyCase`.

The review shows answers, omitted/unavailable steps, status, result/tier ID, score or null, each category's score/null plus answered/applicable/minAnswers, ordered visible question IDs and ordered resolved section IDs. **Save reviewed expected result** creates a new case; Cancel or Escape writes nothing. Changing any answer/name or the draft invalidates the prepared review and preserves current inputs. Do not offer replacing an existing baseline in this increment. Existing legacy missing category/section fields stay absent; their separate reviewed upgrade flow remains unchanged. The baseline detects regressions, not whether the original answer or commercial recommendation is correct.

Keep one combined **25-case** library per quiz and the existing storage key for continuity (its historical `:v1:` suffix is a key name, not proof of the envelope version). Read old version-1 envelopes unchanged. Write version 2 only when the library contains a manual variant; read version-2 mixed libraries with the strict case union. Do not create a second hidden library that evades the 25-case cap or destructively rewrite data on load. Unknown/newer versions or malformed current libraries fail closed and remain in storage.

Extend `pippi-journey-cases` transfer to explicit version 2 for files containing typed cases, while still accepting and exporting choice-only version 1. Version-1 documents may not smuggle typed entries; version-2 manual entries require the new strict fields. Maintain exact legacy assertions, canonical duplicate detection, conflicting same-ID rejection, same-quiz restriction, canonical ISO metadata and original creation timestamps. Imports preserve literal supplied expectations; they do not score or rebaseline. A structurally valid old fixture whose current question was deleted can still be imported for a meaningful failed regression, rather than guessed against a new question.

Retain **128 KiB actual UTF-8 bytes** for incoming/outgoing files, fatal UTF-8 decoding, compact confirmation revalidation and **500,000 JavaScript string characters** for local serialization. The latter is not a 500 KiB byte quota. Combined names, answers and metadata must still fit; report oversize instead of truncating. A large valid local library can remain usable even when export is too large.

Manual confirmation should reread the exact raw localStorage baseline immediately before append, validate the current library, and compare it with the reviewed baseline. Listen for cross-tab storage changes and mark reviews stale. Reuse this narrow check for any touched save path so a new manual save cannot overwrite a newer finite/import case. Existing `persistFixtures` writes a supplied list without such a baseline check; import currently adds its own precheck. One `setItem` is all-or-nothing, **not cross-tab compare-and-swap**: retain the documented concurrent-write limitation; do not claim transactional multi-tab safety or redesign backend sync in this batch. Quota/read failures leave the previous bytes and review/input available for retry.

## Privacy and user interface limits

This tool never loads submissions/contact records, calls an API, creates attempts, sends email, tracks answers or publishes cases. Values remain in volatile composer state until explicit save, then browser-local plaintext; JSON export includes them. Say **synthetic numbers/text you entered**, replacing existing misleading “option IDs only” export/storage copy when manual cases are present. A short-answer field can contain personal information despite its type; an allowlist cannot prove anonymity. Require a clear synthetic-only acknowledgement before saving/exporting a typed case, and do not market this as a redactor or safe storage for customer data. Never inject text as HTML or produce links from it; diagnostics should identify fields/IDs rather than echo all contents.

Keep the default map and finite checks unchanged; the extra composer opens only on request. Separate question inputs from reviewed output, show readable field/type errors, retain work across review cancel, and use a connected enabled focus fallback. A quiz switch/unmount discards volatile manual input and cancels scheduled results so it cannot populate another quiz. Existing dialog Escape/import/expanded-review priorities need one additional deliberate manual-review level, with no nested modal trap. Saving/input changes must not steal focus from a newer edit.

## Acceptance and ownership for a later implementation

**Pure fixtures:** use literal expectations plus parity with the actual evaluator. Cover numeric values just below/at/above branch thresholds and min/max; negative/zero/decimal/scientific lexemes; empty and malformed numeric values; `1` vs `1.0`/`01` exact grading; step mismatch honestly unchanged; required/optional blanks; case/outer-whitespace and contains/not-equals text routing; bounded Unicode/multibyte/control inputs. Cover branch reveal/hide/jump, removal of now-hidden answers, first-rule precedence, unknown vs zero category coverage, min-answer changes, same overall score with changed categories, and ordered conditional result changes. Required contact/challenge/file inputs must remain blocked; optional ones are never saved or silently tested. Guard all fetch/storage/server helpers to prove no runtime side effects during evaluation.

**Persistence/transfer:** unchanged legacy/v1 roundtrips and narrower expectations; mixed v2 roundtrip; forged type markers, unknown properties, mismatched typed IDs/type changes, duplicate/overlapping keys, invalid arrays/booleans, same-ID conflict and foreign quiz; true 128 KiB UTF-8 boundaries versus 500,000-character local boundaries; 25 combined cases; exact preservation on malformed existing storage, quota failure, cancelled review, stale draft/answers/library, late scheduled result and quiz switch. Test imported expected values are never recomputed to current values. Keep all current journey/expanded/transfer suites unchanged in meaning.

**Compiled browser:** one synthetic quiz mixing choices, number and short-answer branch/keyed grading. Author below/at/above and text cases, inspect explicit full baseline, cancel/reopen, save/reload/rerun, edit the draft and observe the precise failed expectations, export/import into a fresh browser context and reject stale reviews. Test mobile 320/390px and desktop keyboard paths, optional omission, errors remaining visible, focus restoration and no outside-focus theft. Intercept/assert zero mutation requests, public starts, email or provider calls. These are individual synthetic cases, not exhaustive number/text domains, human usability proof, production verification or new conversion evidence.

Exclusive implementation scope can stay in new `lib/manual-journey.ts`, a small shared strict fixture codec if needed, `lib/journey-fixtures.ts`, `lib/journey-fixture-transfer.ts`, `components/ConversationMap.tsx` (optionally a focused new manual-input child), narrow evaluator comments/errors only, journey tests and the feature note. **No edits to schema, engine, scoring, marketing, player, publishing, respondent APIs, packages or credentials.** Coordinate two owners only if the codec contract is agreed first; root retains build/server/staging. Do not begin implementation solely from this design note.

## Independent-review migration guards

These are required refinements to the proposed codec and rerun design, based on the current implementation; they are not implemented behavior.

1. **Preserve the legacy local reader and original bytes.** `parseJourneyFixtures` is more permissive than the transfer codec: it accepts bounded but noncanonical metadata, unknown fields, and duplicate option IDs in answer arrays. Replacing that reader wholesale with the stricter transfer parser would make previously readable libraries fail to load. Preserve existing version-1 reads and bytes; apply strict mixed-library validation before promotion or append. If that validation fails, retain the data and report why the operation cannot proceed—do not strip fields, deduplicate answers, normalize metadata, or rewrite the library automatically. Reserve `inputVersion` and `typedAnswers` for the new representation: reject these keys in version-1 envelopes/cases instead of silently ignoring purported manual inputs. Regression fixtures must distinguish tolerated historical unknown fields from these newly reserved manual keys, and prove failed promotion/append preserves the exact stored string.
2. **Validate both answer maps every time a version-2 case runs.** Current `runJourneyFixture` evaluates only `fixture.answers`; the evaluator itself can accept an identifier-shaped string as a short-text answer. A new runner cannot simply retain that call or merge unchecked maps. Revalidate every supplied finite answer against the current exact finite question type and current option IDs, and every typed answer against its recorded exact `number`/`short_answer` type and representation limits. Reject missing/ambiguous IDs, changed types, invalid or duplicate selections, overlapping map keys and unsupported values before the merge. Never silently omit `typedAnswers` or let a finite option-ID string become a text answer after a type change. Test both directions of type changes, removed/renamed options, skipped supplied fields, and reruns after reload/import; errors must identify the invalid saved input without rebaselining expectations. Legacy narrower expectations remain narrower.
3. **An already-open old tab remains an old writer.** Sharing the historical storage key preserves continuity, but an older application tab can still blindly serialize its cached version-1 list over a newly saved mixed library. New-code baseline checks cannot constrain that old code. Tell creators to refresh or close older Pippi editor tabs before using manual cases; do not claim automatic migration is safe across mixed application versions. Test new-code raw-baseline guards by changing the stored string after review and asserting confirmation refuses to write while retaining inputs and the newer bytes. Also document that a simulated old blind writer can still overwrite the shared key; neither a storage event nor the new precheck makes that write atomic or recoverable. This limitation must remain explicit until a separately designed storage/version coordination mechanism replaces it.

Documentation-only update. No application code, tests, storage or servers were changed or run for these guards.
