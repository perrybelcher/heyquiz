## Guest-claim recovery correction found in final browser review

After the original guest test passed its save assertions, screenshot review exposed a false “unsaved edits” recovery banner. A stronger assertion reproduced it against the unchanged candidate. Guest claim had left a session-storage copy whose fingerprint differed only because the server added createdAt. Independent review also found that claim success marked latest edits as saved and unconditionally removed shared local storage, even if edits arrived after the submitted request.

The narrow correction excludes server-created timestamp metadata from the canonical content fingerprint, captures the exact submitted snapshot, and removes only browser copies matching that confirmed snapshot. Each storage area is handled independently. Newer same-tab/other-tab copies and a different guest draft pointer remain available. The existing authenticated PUT drain/conflict logic stays unchanged. The unchanged-claim browser test and all seven focused cases passed on the rebuilt candidate: newer edits during claim followed by actual recovery/save/reload; other-tab same-ID/different-ID pointers; blocked local cleanup; and401/409/503 save failures. Existing draft-safety checks also passed, including all five preview paths, delayed/failed PUTs, shared failures and checkpoints. Before-fix assertion and screenshot are retained separately. Evidence is recorded in final-status.json; no real account or email is used.

Independent final review found no blocking data-loss issue. A separate, untested UX edge remains: cancelling the browser’s navigation warning after editing during a successful guest claim can leave the guest screen showing “Saving”; retrying the claim may conflict because the first snapshot already exists. Backups and the confirmed server snapshot remain intact. Reproduce and repair the cancelled-navigation continuation in the next bounded pass; do not describe it as covered by the accepted-navigation tests.
