## One recommendation

Add an **optional “Plan a test” handoff from the existing weak-step insight in Results to the existing experiment setup**, carrying a reviewed, owner-verified aggregate evidence snapshot. This closes a specific remaining part of acceptance item 10 and makes item 7 actionable. It adds nothing to ordinary blank/template creation and does not add another wizard, AI request or automatic mutation.

The concrete gap is visible in source: `ResultsChart.tsx` shows “A step worth reviewing” with the number of quiet unfinished sessions, but offers no experiment handoff. `Experiments.tsx` asks the creator to supply the hypothesis/change manually, and `ExperimentPlanSchema` stores no supporting evidence. The creator must currently remember the wording, filters and denominator while switching screens. The earlier `overnight-experiment-next-pass.md` proposed this bridge; batch 8 deliberately implemented only the manual plan. This recommendation is the deferred bridge, not a repeat of batch 8.

Prefer this over another broad builder or branding feature. It uses existing measurement and controlled testing to support the product's persuasion positioning, while making no claim that wording caused an exit or that Pippi improves conversion. A real hosted-account/mailbox check and unaided creator study remain more important release gates, but neither is replaced by another local implementation and both are outside this lane's scope.

## Bounded experience and data contract

1. Offer the action only for a measured question with at least one quiet session. Keep the exact counts visible; do not rank a tiny sample as a proven conversion problem. Zero or uninstrumented data offers no fabricated suggestion. Manual experiment setup remains available.
2. Open the existing experiment page with validated **selectors only**: source quiz, stable question/wording identity and the current date/source/campaign/publication filters. Never accept counts, generated hypothesis text or a claimed evidence snapshot from URL parameters. Load owner-scoped evidence on explicit navigation, not during typing.
3. Show the selected wording, cohort, actual UTC cutoff/observation time, reached count, instrumented count and quiet count. Define quiet as an unfinished tracked session with no activity for at least 30 minutes. These are quiz sessions, not unique people, confirmed abandonments or the experiment's assigned-browser denominator. Show any missing instrumentation explicitly. Do not use landing counts in this card.
4. Allow one editable plain-text hypothesis starter and intended-change prompt. Frame clarification/effort/relevance as possibilities the creator must assess; do not diagnose the cause, rewrite a quiz or promise lift. The creator chooses and publishes the second variant through existing tools. If the source step no longer exists with that wording in the chosen published source arm, explain the mismatch and require explicit resolution or removal of the evidence; do not silently retarget to a similarly named question.
5. Use the existing review-before-launch step. Freeze the reviewed evidence alongside the immutable plan only after successful launch; cancel/Back/failure must preserve pending text and create nothing. An explicit Refresh evidence may change the observation and must invalidate the prior review without overwriting the creator's hypothesis/change. Show the frozen supporting evidence on subsequent experiment views. Existing/legacy tests remain unchanged and simply have no recorded supporting evidence.

**Stable identity needs one narrow correction.** Analytics currently uses a question ID alone when there is one wording, but a hashed suffix when multiple wordings are present. That row ID changes when a second wording enters the selected cohort. Add a separate stable wording key from the existing exact `[question.type, question.title]` grouping, and preserve existing row IDs/CSV behavior. Never parse the displayed ` (earlier wording)` suffix. Keep historical wording separate and distinguish current draft wording from the actually published arm.

**The reviewed evidence must be server-authenticated and publication-bound.** The owner-only preview endpoint computes a strictly allowlisted aggregate snapshot and a short-lived, purpose-separated proof bound to the owner, source quiz, normalized selectors, exact selected published-variant digest and evidence snapshot. Evidence must come from that exact publication, not merely matching quiz/question IDs or title. If the analytics selection spans publications, explicitly narrow and recalculate the displayed evidence before review; never silently attach mixed-publication counts to one arm. Launch checks the same published digest before persisting the exact reviewed aggregate.

Source eligibility must also consult durable lifecycle/retirement evidence. Deleting and recreating the same quiz ID must invalidate the old review even if its title, snapshot bytes or timestamps are copied back. Comparing timestamps alone is insufficient. Recheck ownership, retirement/incarnation binding and publication at launch; an old proof must not become valid for a recreated source.

Keep proofs, their raw signed payloads and signatures out of URLs, analytics/experiment DTOs and logs. Define the protected proof transport separately from the allowlisted display response before implementation; do not serialize a bearer proof into ordinary page props or report data. Every evidence read endpoint is owner-only with `Cache-Control: private, no-store`, including error responses. Use established server signing configuration with a distinct purpose, no new credential or provider. Missing signing configuration fails this optional path visibly and leaves manual setup usable.

Do not persist attempt IDs, answers, contacts, session tokens or raw referrers. Keep titles/cohort labels as bounded plain text. Later traffic must not cause the server to silently substitute new counts for the reviewed snapshot: the evidence is an observation at a stated time, not live experiment results. Revalidation may reject an expired proof or changed/retired source and request another explicit review. No new record collection, background job or measurement event is needed.

## Suggested exclusive implementation scope

- **Evidence/model owner:** new `lib/experiment-evidence.ts` for client-safe strict contracts; new server-only evidence helper for owner-scoped aggregation/signing; new `app/api/forms/[id]/experiment-evidence/route.ts`; narrow stable-wording-key addition in `lib/analytics.ts`; narrow launch validation in `lib/experiment-plan.ts` and `app/api/experiments/route.ts`; optional evidence type in `lib/experiments.ts`. Preserve allocation, stats and lifecycle semantics.
- **UI owner, after the contract is agreed:** `components/ResultsChart.tsx`, `components/Experiments.tsx`, and narrow `app/experiments/page.tsx` selector handling; a small evidence-card component if it keeps the main components simpler. Add dedicated unit/API/browser tests and one feature note. Root owns combined staging/build/runtime acceptance.
- Do not touch schema, scoring, player, respondent/start/assignment routes, editor/checklist, template copy, email, CRM or Stripe. `PATCH /api/experiments/[id]` stays pause/resume-only; saved evidence and plan cannot be replaced after launch.

## Acceptance before calling the bridge complete

- Literal cohort fixtures reconcile evidence counts with the existing analytics result for source/campaign/publication/date filters, preview exclusion, quiet exactly at the 30-minute boundary, unknown instrumentation and zero data. Keep the experiment's assigned-browser rates unchanged.
- Rename/reorder/removal and an additional historical wording cannot retarget the chosen step. Earlier draft versus current published wording is explicit. Mixed-publication cohorts are explicitly narrowed before review, and the evidence binds the exact selected published-arm digest. Publication changes fail safely; deletion/recreation with copied snapshot bytes/timestamps, foreign ownership and expired/tampered/wrong-purpose evidence fail closed. Client-supplied totals never override the server observation.
- New traffic after evidence review leaves the reviewed observation unchanged. Explicit refresh requires review again. Aborted or out-of-order loads, filter changes, navigation, expired proofs and 409 responses preserve creator text and cannot attach a stale selection. No write occurs before confirmed launch.
- Round-trip saved evidence stays immutable and contains only allowed aggregate metadata; legacy experiments and ordinary manual setup behave exactly as before. Strict byte/field limits apply before parsing requests. Assert private/no-store responses and absence of proof payloads/signatures from URLs, DTOs and logs.
- Isolated compiled browser acceptance: Results → prefilled plan → editable review → cancel/no-write → launch → reload/frozen evidence; failures and published-version conflict; keyboard/focus and 320/390px reflow. Re-run existing experiment assignment/lifecycle/plan regressions, not a broad unrelated suite. No production traffic is needed.

This slice still does not create a variant, verify a single-change diff, prove causation, calculate significance, pick a winner, stop/promote a test or close production/human-usability acceptance. Existing full owner-record scans also remain a scale limit; the bridge must not add per-keystroke scans or imply that an aggregate evidence card solves query/index design.
